## What this repo is

A series of small, reproducible experiments about what happens to writing when
machines read it as often as people do.

- **Part 1 (`01-cost/`): cost.** A notebook measuring what text costs a model to
  read. Complete. Do not change its logic or results; moving files is fine.
- **Part 2 (`02-comprehension/`): comprehension.** Does rewriting a document for
  clarity, with the same facts, make a model's answers more accurate? In progress.
- **Later parts:** findability (retrieval) and actionability (agents). Not started.
  Keep them out of scope, but leave room for them.

## Accuracy and verification come first

This project produces numbers other writers will cite. One wrong figure undermines
the series. Accuracy outranks speed, polish, and scope at every step.

- **Never guess.** Verify model names, API parameters, SDK methods, and pricing
  against official docs before use. Record the source URL and date checked.
  If something cannot be verified, stop and ask Reem.
- **Every number is traceable.** Every figure in a report, chart, or README is
  generated by code from `raw.jsonl` or `scores.csv`, never typed by hand.
  `summary.md` states which run id and which files each number came from. Reruns
  on the same raw data produce identical scores and reports.
- **Check before reporting.** Sanity checks fail loudly: answer counts match
  questions x versions x members x models x repetitions x paraphrases; costs
  recomputed from logged tokens match logged costs; percentages match their
  counts. Spot-check raw answers against scores before calling a milestone done.
  A human reviews the judge sample before any result is published; report judge
  agreement alongside results.
- **Protect the data.** Never silently drop, fix, retry-and-overwrite, or filter
  results. Log every failed call, parse error, and exclusion with its reason, and
  show the counts in the report. Never edit files under `docs/` to make results
  look cleaner.
- **Say what you don't know.** Report sample size, number of docs, judge error,
  model version drift, and pricing date plainly. Verify surprising results before
  treating them as findings.
- Each milestone ends with a short verification note: what was checked, how, and
  what is still unverified.

## Guardrails

- Never commit API keys. `.env` is gitignored; `.env.example` documents the vars.
- Only include source docs whose license permits redistribution. Record the
  license per member in `set.yaml`. Refuse to run a set with a missing license.
- Keep raw results in the repo so anyone can audit scoring.
- Do not add anyone as a collaborator or credit them in the repo without Reem's
  approval.
- No paid API calls in CI. CI runs validation only.

## Design: doc sets (amendment 01)

Part 2 tests two things a single-doc test would miss:

1. **Confusability.** Real docs contain similar but not identical content (same
   procedure across versions, platforms, or products). Can the model pick the
   right one?
2. **Consistency.** One correct answer can be luck. A model that understood the
   source answers correctly across many similar but not identical queries.

So the unit is a **set** of 3 to 5 similar but distinct source docs (**members**).
All members of a set are loaded into context together, so the model must tell
them apart.

### Structure

```
02-comprehension/docs/
  <set-slug>/
    set.yaml            # coverage, how members differ, per-member license+source, version definitions
    questions.yaml      # each question names its target_member
    paraphrases.yaml    # query variations per question
    members/
      <member-slug>/
        facts.yaml         # fact inventory for this member
        differences.yaml   # facts that distinguish this member from its siblings
        versions/
          original.md
          <rewrite-name>.md
```

- **Version names are defined per set** in `set.yaml`, not hardcoded. `original`
  is required. One rewrite type is supported now: **`differentiated`**, which
  makes each member's distinguishing settings explicit with clear labels.
  Methodological rule: the differentiated version labels a member's *own*
  distinguishing facts (for example "Team default"); it must not import a
  sibling's specific values, because that would add information. Writing changes
  only, never information.
- A version applies to the whole set. Every member uses the same version in a run.

### Data formats

`facts.yaml`: `- {id: f03, fact: "..."}`

`differences.yaml`: `- {fact_id: f03, note: "how this member differs from siblings"}`

`questions.yaml`:
```yaml
- id: q01
  target_member: tarpon-team
  question: "..."
  answer: "..."              # reference answer
  key_points: ["...", "..."] # what a correct answer must include
  type: direct               # direct | trap
  depends_on_facts: [f03]    # ids from the target member's facts.yaml
```
A `trap` question is answered correctly only if the model connects an instruction
to a caveat or exception elsewhere in the doc.

`paraphrases.yaml`:
```yaml
- question_id: q01
  paraphrases:
    - id: q01-p001
      text: "..."
      source: human            # human | generated
      review_status: approved  # pending | approved | rejected
      reviewed_by: "..."
      generation_prompt: "..." # required when source == generated
      generation_model: "..."  # required when source == generated
```
Paraphrases preserve meaning exactly. A generated paraphrase never runs in a
published run until a human approves it; unapproved paraphrases run only in
clearly labeled draft runs. A paraphrase that changes the question is rejected,
not silently rewritten. Record the generation prompt and model for every
generated paraphrase.

### Validation (`src/validate.py`)

- All YAML validates against the schemas in `02-comprehension/schemas/`.
- Every member has `facts.yaml` and `differences.yaml`; every listed difference
  maps to a real fact id.
- Every question's `target_member` exists; every `depends_on_facts` id exists in
  that member's facts.
- Every paraphrase's `question_id` exists; generated paraphrases carry a
  generation prompt and model.
- Every member has a license. Refuse to validate a set with a missing license.
- **Fact inventory (the most important guardrail):** every version of every member
  contains exactly the same facts as its original. Rewrites change writing only,
  never information. The simple check (CI-safe, no API) confirms structure and
  emits a per-version human-review checklist. An optional LLM check that lists
  facts missing or added per version is added with the runner (it needs the API,
  is off by default, and never runs in CI).

### Scoring labels

`correct | partial | incorrect`, plus:
- **`wrong_sibling`**: incorrect for the target member but matching a sibling's
  facts. The core confusability metric. The judge receives the target's reference
  answer and key points plus siblings' distinguishing facts so it can detect this.
- **`confident_wrong`**: incorrect with confidence 4 or 5. The headline metric.

The judge is blind to version and model, and uses a model from a different family
or tier than the one being scored where possible. Record which judge was used.
The human spot-check sample includes `wrong_sibling` cases; the report shows judge
agreement for that label separately.

### Metrics

- **Consistency rate** per question: share of its paraphrases answered correctly.
- **Worst-case paraphrases** per question: the wordings that failed, verbatim.
- **Sibling confusion rate** by version: how often `wrong_sibling` occurs.
- Accuracy by version and model; trap vs direct; confident-wrong rate.
- Report paraphrase variance and repetition variance separately. With many
  paraphrases, repetitions can default to 1; keep it configurable.
- With a small question set, report counts alongside percentages. Avoid
  statistical language the data cannot support.

### Cost and scale

- `estimate.py` is a dry run: token counts and cost by set, version, model, and
  paraphrase count, compared to the budget ceiling in `config/run.yaml`. Use
  Anthropic `count_tokens` for Claude and `tiktoken` for GPT (tokenizers differ).
  Refuse to run above the ceiling without explicit confirmation.
- Prompt caching on set content, since it is reused across many questions.
- Evaluate batch APIs for large runs; verify availability, pricing, and params
  against official docs first and record source and date.
- Support a sample mode (for example 10% of paraphrases) to test the pipeline
  before a full run.

## Runner and outputs (later milestones)

- Models in `config/models.yaml` with pricing and pricing date. Defaults to
  verify against docs before use: `claude-haiku-4-5-20251001`, `claude-sonnet-5`,
  `claude-opus-5`, plus one current OpenAI model (check the OpenAI docs for the
  current name).
- The set content goes in the system prompt with prompt caching on Anthropic
  calls. Fixed instruction: answer using only the provided documentation; return
  JSON with `answer` and `confidence` (1 to 5).
- Run each question N times (default 3, configurable) to capture variance. Log
  temperature.
- `raw.jsonl` logs every call: run id, set, member, version, model, question id,
  paraphrase id, repetition, answer, confidence, tokens in/out, cached tokens,
  latency, cost. Resume safely after interruption; handle rate limits with
  backoff.
- `results/<run-id>/`: `raw.jsonl`, `scores.csv`, `summary.md`, `charts/`.

## Writing rules for public prose (READMEs, CONTRIBUTING, summaries)

- Plain language, light on jargon. Define terms like "token" or "prompt caching"
  in one short phrase the first time.
- No em-dashes.
- Avoid "it's not x, it's y", "not x. Not y. But z", and "load-bearing".
- No sweeping generalizations ("nobody does this", "everyone gets this wrong").
- Direct and warm. A little humor is fine.
- The part 2 README opens with the question it answers, then how to run it in
  under five commands, then how to contribute.

## Build order (check in with Reem after each milestone)

0. Restructure the repo. Done.
1. Scaffold `02-comprehension/`, schemas, and `validate.py` with one placeholder
   set. (Current milestone.)

4. Full run across all models and versions.
